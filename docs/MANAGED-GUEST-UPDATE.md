# Managed guest update checkpoint coordinator

`app/managed_guest_update.go` is a dormant safety component. No current launcher path calls it. It does not install packages, change the guest disk, change the release manifest, or treat the guest's generic `ready` signal as proof that a package update succeeded.

`Prepare` authenticates a signed guest update plan and its baseline release manifest, checks the installed guest payload receipt, hashes the installed boot payload files against the authenticated baseline, requires a stopped guest disk, and creates a full bootable checkpoint. It then publishes `.managed-guest-update.json` durably with the plan digest and exact checkpoint ID, archive digest, and size. A failed or low-space checkpoint publishes no update journal. A completed checkpoint left by a crash before journal publication is an unused snapshot; package writes cannot be authorized from it.

`RecoverPending` is the explicit API a future startup path must call **before allowing any VM launch**. A pending journal triggers full checkpoint rollback. Missing, changed, or corrupt checkpoints leave the journal in place and block that path. Recovery compares the restored architecture with the checkpoint architecture pinned in the update journal; it does not read the current build specification. It uses the format and exact disk basename captured from the verified pre-update disk instead of parsing a possibly torn active QCOW2 header. For a portable QCOW2 installation it runs the `qemu-img` restored from the fully hash-verified checkpoint, not the possibly torn current runtime. The existing snapshot rollback journal handles interruptions during the directory swap. A repeated recovery is safe because the VM has not been allowed to run while the update journal remains.

The exact active disk file must still exist as a regular, non-linked file so recovery can acquire its exclusive stopped-VM handle. A missing disk or an unexpected second disk fails closed with the journal retained.

The coordinator and checkpoint store each use their existing local mutation locks, and the exclusive disk open rejects an orphaned VM process. Future wiring must also hold the launcher lifecycle lock across preparation, package writes, recovery, and startup. The coordinator currently checks the installed boot payload receipt; it does not yet prove the plan's `managedPackages` versions inside the guest. A product updater still needs authenticated package download, a guest package-state preflight, a bounded transaction runner, a specific post-update health check, and a durable commit operation. Generic guest readiness must not clear the journal.

Preparation rejects an existing payload or launcher update journal. Managed recovery still uses the checkpoint store's rule that those separate journals must be settled before rollback. A future executor must coordinate boot-asset staging with this journal instead of leaving a second pending update state for managed recovery to guess about.

The CI old-disk upgrade and package-write interruption tests validate disposable images and offline backup restoration. They do not activate this coordinator in an installed Omarchy app. This component therefore provides a checkpoint and recovery foundation, not an automatic update or rollback feature for users yet.

## Disposable recovery test, 2026-09-27

On Windows, `QEMU_IMG` pointed to the stopped Candidate8 runtime's `qemu-img.exe` (SHA-256 `bf9c25bd2b50b5296220f21c72eb3784a7d270ac8a9fcce14dce2031acac5efe`). `TestManagedGuestUpdatePortableRecoveryUsesRestoredTool` copied that executable and its 21 sibling DLLs into a temporary fixture, created a portable QCOW2 disk and checkpoint, then corrupted only the fixture's active QCOW2 header, build specification, `qemu-img.exe`, and DLLs. Recovery passed, produced a backing-free QCOW2 disk, and a separate `qemu-img convert` comparison found the original logical disk bytes. The full app `go test .` suite also passed with that test tool configured. No VM was launched and no installed disk or runtime was changed.
